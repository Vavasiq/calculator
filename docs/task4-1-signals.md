# ДЗ-4. Задача 1 — обработка системных сигналов

План изменений для задачи 1 из [task4.md](../task4.md).

**Критерий готовности (из задания):** приложение завершает работу после получения `SIGTERM`.

**Дополнительно в этой задаче:**
- в приложении минимум 2 потока: поток сигналов и рабочий поток;
- по `SIGTERM`/`SIGINT` рабочий поток останавливается штатно, а деструкторы закрывают соединение с PostgreSQL (`PQfinish`);
- флаг остановки передаётся между потоками без гонок данных, что проверяется ThreadSanitizer.

**Вне рамок задачи:** systemd-юнит (задача 2), сеть на Boost.Asio (задача 3), deb-пакет (задача 4). План устроен так, чтобы задача 3 встраивалась без переделки механизма остановки (см. раздел 7).

---

## 1. Текущее состояние

[src/main.cpp](../src/main.cpp) работает в одном потоке:

1. Проверяет `argc == 2`.
2. Создаёт `calculator::Runner`: подключается к БД и прогревает кеш.
3. Выполняет `runner.run(argv[1])`.
4. Вызывает `waitForTerminationSignal()`: `sigprocmask` блокирует `SIGINT`/`SIGTERM`, затем `sigwait`.
5. Возвращает статус расчёта, после чего деструктор `Runner` закрывает соединение.

**Проблемы относительно задачи:**
- поток один, а нужно минимум два;
- маска сигналов ставится только после расчёта, и `SIGTERM` во время подключения к БД или расчёта убивает процесс без деструкторов;
- задание из `argv` обязательно, хотя сервис под systemd (задача 2) будет запускаться без аргументов.

## 2. Целевая модель потоков

| Поток | Кто создаёт | Что делает | Чем владеет |
|---|---|---|---|
| `main` | ОС | Блокирует сигналы, создаёт два потока, ждёт их завершения (`join`), возвращает код выхода | `StopFlag`, `SignalThread`, `WorkerThread` |
| Поток сигналов | `SignalThread` | `sigwait` на `{SIGINT, SIGTERM}`, затем `stopFlag.requestStop(...)` и выход | Ничем, только ссылкой на `StopFlag` |
| Рабочий поток | `WorkerThread` | Создаёт `Runner` (подключение к БД + прогрев кеша), обрабатывает задание, ждёт остановки, выходит, после чего `~Runner` закрывает БД | `Runner` → `DataBase` → `PgConnection` |

`main` нарочно делает только оркестрацию. Так оба потока из требования — отдельные именованные `std::thread`, и это видно и в коде, и в выводе `ps -T`. Итого в процессе 3 потока.

**Ключевой инвариант:** объекты БД (`Runner`, `DataBase`, `PgConnection`) создаются, используются и уничтожаются только в рабочем потоке. Других потоков у них нет, поэтому мьютексы в `DataBase` не нужны, а требование libpq «один `PGconn` — один поток в каждый момент» выполняется само собой.

### Последовательность при `SIGTERM`

```
main            поток сигналов              рабочий поток
 │ блокирует SIGINT/SIGTERM (до любых потоков)
 │──создаёт──▶ sigwait(...)  [ждёт]
 │──создаёт────────────────────────────────▶ Runner(): connect + warmUpCache
 │                                           run(json), если задание передано
 │ worker.join() [ждёт]                      stopFlag.waitForStop() [ждёт на cv]
 │                │
 │   ◀── SIGTERM от ОС / systemd
 │                │ requestStop(Signal, SIGTERM)
 │                │   └─ notify_all ───────▶ просыпается, выходит из функции
 │                │ выход                    ~Runner → ~DataBase → PQfinish
 │ ◀────────────────────────────────────── поток завершён
 │ signals.join()
 │ return 0
```

## 3. Блокировка маски сигналов

- **Первая строка `main`**, до создания любых потоков и до первого обращения к `Logger` (на всякий случай): `pthread_sigmask(SIG_BLOCK, {SIGINT, SIGTERM})`. Вместо `sigprocmask` берём `pthread_sigmask`, потому что поведение `sigprocmask` в многопоточной программе не определено.
- **Зачем до потоков:** новый поток наследует маску создателя. Если хоть у одного потока сигнал не заблокирован, ядро может доставить ему процессный `SIGTERM`. Тогда сработает действие по умолчанию: процесс завершится без деструкторов, и `PQfinish` не вызовется.
- **`sigwait` безопасен:** сигнал принимается синхронно, как обычный вызов функции, а не через асинхронный обработчик. Поэтому в потоке сигналов можно логировать, брать мьютекс и звать `notify_all`. Ограничения async-signal-safe здесь не действуют.
- **Нет гонки «сигнал до `sigwait`»:** сигнал, пришедший до вызова `sigwait` (например, во время подключения к БД), остаётся в очереди ожидающих и будет получен первым же `sigwait`.

## 4. Флаг остановки: `condition_variable`, а не `std::atomic`

**Выбор:** `std::mutex` + `std::condition_variable` + `bool stopRequested_`, к которому обращаются только под мьютексом.

**Почему не только `std::atomic<bool>`:** в задаче 1 рабочему потоку после расчёта нечего делать, кроме как ждать остановки. С голым атомиком пришлось бы опрашивать его в цикле со `sleep`, а это лишняя задержка и холостая нагрузка на CPU. `condition_variable` будит поток ровно в момент запроса.

**Как избежать гонок и потерянных пробуждений:**
- флаг ставится под мьютексом (`lock_guard`), `notify_all` вызывается после записи;
- ожидание идёт только через `cv.wait(lock, predicate)`, где предикат — `stopRequested_`. Если `requestStop` случился до `waitForStop`, предикат сразу истинен и пробуждение не теряется. Ложные пробуждения тоже обрабатываются;
- `requestStop` идемпотентен: побеждает первая причина, повторные вызовы ничего не меняют.

**Причина остановки** хранится вместе с флагом под тем же мьютексом:
- `Signal` + номер сигнала — пришёл `SIGTERM`/`SIGINT`;
- `Error` — рабочий поток упал при инициализации, например нет связи с БД.

`main` использует причину, чтобы решить, нужно ли будить поток сигналов (раздел 5), и для лога.

## 5. Завершение без зависаний

**Сценарий 1 — пришёл сигнал (обычный путь):**
1. Поток сигналов вызывает `requestStop(Signal)` и выходит.
2. Рабочий поток просыпается и выходит, после чего `~Runner` закрывает БД.
3. `main` делает `join` обоих потоков и возвращает `0`.

**Сценарий 2 — рабочий поток завершился сам (ошибка):**
1. Исключение из `Runner()` или `run()` ловится внутри функции потока. Иначе `std::terminate` убьёт процесс без деструкторов.
2. Рабочий поток пишет ошибку в лог, сохраняет код выхода `1` и вызывает `requestStop(Error)`.
3. Поток сигналов в это время всё ещё висит в `sigwait`. Сам он не проснётся, и `join` зависнет. Поэтому `SignalThread::stop()` проверяет причину: если остановка пришла не от сигнала, поток будится через `pthread_kill(signalThread.native_handle(), SIGTERM)`.
4. Это безопасно: сигнал заблокирован и адресован конкретному потоку, `sigwait` его заберёт, а повторный `requestStop` ничего не изменит. Идентификатор потока валиден до `join`, даже если поток уже вышел.

Отклонённая альтернатива — `sigtimedwait` с таймаутом и опросом флага. Это периодический опрос, и задержка выхода равна таймауту.

**Код выхода** пишется рабочим потоком в обычное поле `WorkerThread`, а `main` читает его только после `join()`. `join` задаёт отношение happens-before, поэтому атомик не нужен, и TSan гонку не увидит.

**Изменение поведения:** при штатной остановке сигналом процесс возвращает `0`, а не статус расчёта, как раньше. Для systemd (задача 2) это означает «сервис остановлен успешно». Статус расчёта по-прежнему печатается.

**Повторный Ctrl+C во время остановки** игнорируется: сигналы заблокированы, а поток сигналов уже вышел. Остановка короткая (закрыть одно соединение), так что это приемлемо. В задаче 2 systemd всё равно добьёт процесс по `TimeoutStopSec`.

## 6. Изменения по файлам

### Новые файлы

**`include/calculator/StopFlag.h`, `src/StopFlag.cpp`** — класс `StopFlag`, общий флаг остановки (раздел 4).
- `requestStop(StopReason reason, int signalNumber = 0)` — идемпотентно ставит флаг и будит всех ждущих.
- `bool isStopRequested() const`.
- `void waitForStop() const` — блокирующее ожидание с предикатом.
- `bool waitForStopFor(std::chrono::milliseconds timeout) const` — ожидание с ограничением по времени, чтобы тесты обходились без `sleep`.
- `StopReason reason() const`, `int signalNumber() const`.
- `std::size_t waitingThreads() const` — сколько потоков сейчас внутри `waitForStop`/`waitForStopFor`. Счётчик увеличивается под мьютексом перед `cv.wait` и уменьшается после выхода из него. `cv.wait` отпускает мьютекс атомарно, поэтому значение `1`, прочитанное под мьютексом, гарантирует, что поток уже ждёт уведомления, а не только собирается. Нужен тесту `WakesWaiterFromOtherThread` и логам.
- Поля: `mutable std::mutex`, `mutable std::condition_variable`, `bool`, причина, номер сигнала, `mutable std::size_t` счётчик ждущих. Копирование и перемещение запрещены, потому что на объект ссылаются оба потока.

**`include/calculator/SignalThread.h`, `src/SignalThread.cpp`** — класс `SignalThread`, RAII-обёртка над потоком сигналов.
- `static void blockTerminationSignals()` — блокирует `SIGINT`/`SIGTERM` через `pthread_sigmask`, вызывается первой строкой `main`. Этот же набор сигналов используется в `sigwait`, поэтому он объявлен в одном месте.
- Конструктор принимает `StopFlag&` и запускает `std::thread`. Тело потока: `sigwait`, лог «получен SIGTERM/SIGINT», `requestStop(Signal, signo)`, выход.
- `void stop()` — при необходимости будит поток через `pthread_kill` (раздел 5), затем `join`. Повторный вызов безопасен.
- Деструктор вызывает `stop()`, поэтому поток не останется joinable, и `std::terminate` в `~thread` не сработает.

**`include/calculator/WorkerThread.h`, `src/WorkerThread.cpp`** — класс `WorkerThread`, RAII-обёртка над рабочим потоком.
- Конструктор принимает `StopFlag&` и `std::optional<std::string> initialTask` (JSON из `argv`, если он передан), затем запускает `std::thread`.
- Тело потока, целиком внутри `try/catch`:
  1. создать `Runner` (подключение к БД, прогрев кеша);
  2. если есть `initialTask`, вызвать `runner.run(*initialTask)`;
  3. `stopFlag.waitForStop()`;
  4. выйти из области видимости, после чего `~Runner` закроет соединение.
  
  В `catch`: лог, `exitCode_ = 1`, `requestStop(Error)`.
- `void join()`, `int exitCode() const` (читается только после `join`). Деструктор делает `join`, если поток ещё joinable.

### Изменяемые файлы

**[src/main.cpp](../src/main.cpp)** — целиком меняется порядок работы:
1. `SignalThread::blockTerminationSignals()` — самой первой строкой.
2. Разбор аргументов: `argc == 1` означает режим сервиса без начального задания, `argc == 2` — JSON-задание. Остальное — `Usage` и код `1`.
3. Создание `StopFlag`, затем `SignalThread`, затем `WorkerThread`.
4. Явно `worker.join()`, затем `signals.stop()`. Порядок не зависит от порядка деструкторов.
5. Лог причины остановки, `return worker.exitCode()`.

Функция `waitForTerminationSignal()` удаляется: её роль переходит к `SignalThread`.

**[src/Logger.cpp](../src/Logger.cpp)** — в шаблон spdlog добавляется id потока (`[%t]`). Так в логах видно, какой поток что делает, и это пригодится для демонстрации и разбора отчётов TSan. Логгер уже потокобезопасен: `stdout_color_mt` — это `_mt`-версия, а инициализация статической локальной переменной в `Logger::instance()` потокобезопасна с C++11. Других изменений нет.

**[CMakeLists.txt](../CMakeLists.txt):**
- `find_package(Threads REQUIRED)`, `Threads::Threads` линкуется в `calculator_lib` как `PUBLIC`.
- Новые исходники `src/StopFlag.cpp`, `src/SignalThread.cpp`, `src/WorkerThread.cpp` добавляются в `calculator_lib`.
- `option(ENABLE_TSAN "Build with ThreadSanitizer" OFF)`. При `ON` флаги задаются глобально через `add_compile_options(-fsanitize=thread -g -O1)` и `add_link_options(-fsanitize=thread)`.
  - **Место в файле:** сразу после `option(...)`, **до первого `FetchContent_MakeAvailable`**. Глобальные опции действуют только на цели, объявленные после них, поэтому только так инструментируются и зависимости: `mathlib`, `spdlog`, `gtest`, `nlohmann_json` (header-only, компилируется в наших целях).
  - **Почему не `target_compile_options`:** с ним TSan видел бы только наш код. Синхронизация внутри неинструментированных библиотек (мьютекс логгера spdlog, потоки gtest) была бы ему не видна, а это даёт ложные срабатывания и пропуски.
  - **libpq** приходит из системы через `find_package` и остаётся неинструментированной. Это допустимо: соединение используется только в одном потоке (инвариант из раздела 2).
- TSan несовместим с Valgrind, поэтому при `ENABLE_TSAN` тест `memcheck` не регистрируется. TSan-сборка делается в отдельной директории, например `build-tsan/`.

**[tests/tests.cpp](../tests/tests.cpp)** — новые тесты `StopFlag`. Сигналы тестировать не нужно, но флаг — это та часть, где возможна гонка, и под TSan её стоит прогнать. Ни в одном тесте нет `sleep`:
- `StopFlagTest.InitiallyNotRequested` — свежий флаг не взведён, `waitForStopFor(0ms)` возвращает `false`.
- `StopFlagTest.RequestBeforeWaitIsNotLost` — `requestStop`, затем `waitForStop` возвращается сразу (нет потерянного пробуждения).
- `StopFlagTest.WakesWaiterFromOtherThread` — проверяет именно пробуждение ждущего потока, а не случай «флаг уже взведён»:
  1. Поток вызывает `waitForStopFor(2s)` и пишет результат в `std::atomic<bool>`.
  2. Основной поток **busy-циклом с таймаутом** (дедлайн 2 с по `steady_clock`, в теле только `std::this_thread::yield()`, без `sleep`) ждёт, пока `flag.waitingThreads()` станет равен `1`, то есть поток реально вошёл в `cv.wait`. После цикла `ASSERT_EQ(flag.waitingThreads(), 1)`: если поток так и не начал ждать, тест падает с понятной причиной, а не зависает.
  3. Только после этого основной поток вызывает `requestStop`.
  4. После `join` проверяется, что ожидание вернуло `true`.
  
  Без шага 2 `requestStop` мог бы успеть раньше `wait`. Тогда тест проходил бы через ветку «предикат уже истинен», которую покрывает `RequestBeforeWaitIsNotLost`, а пробуждение через `notify_all` оставалось бы непроверенным.
- `StopFlagTest.FirstReasonWins` — `requestStop(Signal, SIGTERM)`, затем `requestStop(Error)`: причина остаётся `Signal`.

**Без изменений:** `Runner`, `DataBase`, `Postgres`, `Parser`, `Checker`, `Calculator`, `Printer`. Они продолжают работать в одном (рабочем) потоке.

## 7. Как это ляжет на задачи 2 и 3

- **Задача 2 (systemd):** `systemctl stop` шлёт `SIGTERM`, и это сценарий 1 из раздела 5. Запуск без аргументов (`argc == 1`) уже поддержан.
- **Задача 3 (Asio):** в рабочем потоке `waitForStop()` заменится на `io_context.run()`. Чтобы сигнал прервал `run()`, в `StopFlag` добавится подписка на остановку: `onStop(callback)`. Рабочий поток подпишет туда `io_context.stop()`, который потокобезопасен. Поток сигналов и маска не меняются. Здесь же понадобится игнорировать `SIGPIPE`, но это часть задачи 3.

  Правила подписки, чтобы не было потерянных остановок и дедлоков:
  - **Подписка после остановки вызывается сразу.** Если `requestStop` уже случился до `onStop`, колбэк выполняется немедленно в вызывающем потоке, а не сохраняется. Иначе рабочий поток, подписавшийся чуть позже прихода `SIGTERM`, ушёл бы в `io_context.run()` и никогда не остановился. Проверка флага и добавление колбэка в список выполняются под одним захватом мьютекса, поэтому окна между ними нет.
  - **Колбэки вызываются вне мьютекса `StopFlag`.** `requestStop` под мьютексом ставит флаг и **переносит** список колбэков в локальную переменную, отпускает мьютекс, вызывает `notify_all` и только потом выполняет колбэки. Так колбэк может сам обращаться к `StopFlag` (`isStopRequested()`, `onStop`) без самоблокировки, а чужой код под нашим мьютексом не создаёт цикл захвата блокировок, который TSan сообщит как lock-order-inversion. Немедленный вызов в `onStop` тоже идёт после отпускания мьютекса.
  - Каждый колбэк вызывается ровно один раз: список очищается при переносе, а повторные `requestStop` ничего не делают (идемпотентность из раздела 4).

## 8. Проверка готовности

**Сборка:**
```bash
cmake -S . -B build && cmake --build build
ctest --test-dir build                                 # включая memcheck
cmake -S . -B build-tsan -DENABLE_TSAN=ON && cmake --build build-tsan
ctest --test-dir build-tsan                            # тесты StopFlag под TSan
```

**Ручная проверка:**

| Сценарий | Действие | Ожидание |
|---|---|---|
| Штатная остановка | `./build/calculator '{"op":"+","a":1,"b":2}' &`, затем `kill -TERM $!` | Печатает `3`, не завершается сам. После сигнала в логе «получен SIGTERM» → остановка рабочего потока → закрытие соединения; код выхода `0` |
| Ctrl+C | Запуск в терминале, затем Ctrl+C | То же, в логе `SIGINT` |
| Режим сервиса | `./build/calculator &`, затем `kill -TERM $!` | Подключается к БД, ждёт, по сигналу завершается с кодом `0` |
| Количество потоков | `ps -T -p <pid>` | 3 потока: `main`, сигналы, рабочий |
| Нет БД | Остановить PostgreSQL и запустить | Ошибка подключения в логе, код выхода `1`, процесс **не зависает** (поток сигналов разбужен) |
| Сигнал во время старта | `kill -TERM` сразу после запуска, пока идёт подключение или прогрев | Сигнал не теряется, процесс завершается после инициализации, деструкторы отрабатывают |
| Утечки | `valgrind --leak-check=full ./build/calculator '…'`, затем `kill -TERM` | `definitely lost: 0` |
| Гонки | То же для `./build-tsan/calculator` | Нет отчётов `WARNING: ThreadSanitizer` |
